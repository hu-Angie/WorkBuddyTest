## 一、需求对齐过程

需求经过三轮收敛，最终确定为当前方案：

| 轮次 | 用户诉求 | 产出 |
|---|---|---|
| 第一轮 | vibe coding 一个小程序，要 3 个有趣的点子 | 给出娱乐/创意方向 3 案：声波粒子音乐画布、像素星座生成器、赛博电子宠物 |
| 第二轮 | 修正为**主前端 + 一定后端**的产品 | 原 3 案升级为带后端版本（实时/持久化/社区） |
| 第三轮 | 进一步修正方向：**通信相关 / 类工作台 · 效率方向** | 给出新三案：A 实时协作工作台、B 极简实时 IM、C 个人效率指挥台 |
| 决策 | 用户选定 **A** | 即本方案 |

### 第三轮三方案对比（决策依据）

| 维度 | A 实时协作工作台 | B 极简实时 IM | C 个人效率指挥台 |
|---|---|---|---|
| 通信味 | 中（@通知 / 活动流） | **强**（纯实时消息） | 弱（单向推送） |
| 效率味 | **强**（看板 / 任务） | 中（消息转待办） | **强**（个人 dashboard） |
| 前端复杂度 | 高 | 中 | 中低 |
| 后端复杂度 | 中高 | 中 | 低 |
| 最快出活 | 慢 | 中 | **快** |
| 像完整产品 | **最像** | 中 | 中 |

**选定 A 的理由**：同时覆盖「通信」与「效率工作台」两个关键词，前端是产品主体，后端的实时职责明确且有价值。

## 二、最终方案定义

**产品**：实时协作工作台 —— 任务看板 + 即时消息。

**核心功能**

1. 三列看板（待办 / 进行中 / 已完成），卡片可拖拽换状态
2. 任务新建、编辑、删除（负责人、优先级、截止日期）
3. 任务详情面板 + 评论区，支持 `@昵称` 提醒，被 @ 者高亮
4. 实时活动流：所有人的操作滚动展示，最新一条高亮
5. 在线成员头像组与在线人数，成员进出有提示
6. 断线自动重连，恢复后重新拉取全量状态

**架构定位**：主前端 + 一定后端。前端负责全部交互体验；后端只做三件事——**实时广播、数据持久化、在线成员管理**。

## 三、技术方案

### 技术栈（用户授权由我决定，已定）

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | 原生 HTML + CSS + JS | 零构建，浏览器直接预览，符合 vibe coding 快速出活 |
| 后端 | Node.js（Express + `ws`） | 与前端同语言；WebSocket 实时能力成熟 |
| 存储 | JSON 文件（`data/`） | 轻量、零外部依赖，无需数据库 |
| 样式 | light 主题手写 CSS | 与 IDE 浅色主题一致 |

### 架构与文件结构

```
workbuddyTest/
├── server.js            # 后端：Express + WebSocket + 持久化
├── package.json
├── public/              # 前端（零构建）
│   ├── index.html       # 页面骨架
│   ├── styles.css       # light 主题样式
│   └── app.js           # 渲染 / 拖拽 / 详情 / 实时同步
├── data/                # 运行时生成
│   ├── tasks.json
│   └── comments.json
├── 使用说明.md            # 操作文档
└── 项目方案.md            # 本文件
```

### 关键设计决策

1. **UI 由服务端广播统一驱动**：自身操作的 REST 请求不直接改 UI，而是等广播回传后更新，保证多端视图一致、逻辑单一。
2. **防抖写盘（200ms）**：高频操作时合并写入，避免反复落盘。
3. **删除级联**：删除任务时同步清理其评论。
4. **活动流仅存内存**：有意简化，避免无意义落盘，重启即清空。

## 四、接口设计

### REST

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/state` | 拉取全量状态 |
| POST | `/api/tasks` | 创建任务 |
| PUT | `/api/tasks/:id` | 更新字段；`status` 变化时广播 `task:moved` |
| DELETE | `/api/tasks/:id` | 删除任务并级联删除评论 |
| POST | `/api/tasks/:id/comments` | 发布评论，自动解析 `mentions` |

### WebSocket

客户端先发送 `{ "type": "hello", "name": "小明" }` 注册成员。

| 事件 | 触发时机 |
|---|---|
| `init` | 注册成功，下发全量快照 |
| `task:created` / `task:moved` / `task:updated` / `task:deleted` | 任务增删改与状态变更 |
| `comment:added` | 新增评论 |
| `member:joined` / `member:left` | 成员进出 |

### 数据模型

```js
Task    { id, title, desc, assignee, status, priority, due, createdAt, updatedAt, order }
//   status: todo | doing | done      priority: high | med | low
Comment { id, taskId, author, text, mentions[], createdAt }
Activity{ id, type, actor, summary, createdAt }   // 仅内存，最近 50 条
```

## 六、已知取舍

- **活动流仅存内存**，服务重启后清空（任务与评论是持久化的）。
- **无鉴权、无用户体系**，昵称即身份，适合本地或小团队内网试用，不建议直接暴露公网。
- 数据存 JSON 文件，适合演示与轻量使用，不适合高并发。
